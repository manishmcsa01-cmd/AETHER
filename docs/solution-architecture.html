What the system is

AETHER does two jobs that are usually sold as separate products. It is a system of record for every AI agent an enterprise runs — discovering them across platforms, scoring them, costing them, and auditing them. And it is a clearing layer for what those agents do to each other: identity, delegated authority, reputation, escrow, and recourse.

The first job is a dashboard problem and a crowded market. The second is infrastructure, and it is the reason the system exists. Before an agent hands money or authority to another agent, four questions have to be answerable with evidence rather than self-report: who is this, who authorized it, what is its record, and who pays when it goes wrong. That is the architecture below.

Governing principle

Language models advise. Code enforces.

Six LLM supervisory agents produce narrative analysis — risk write-ups, audit summaries, cost recommendations. None of them can approve or block anything. Every enforcement decision runs through a deterministic policy engine and a signature check, so the same inputs always produce the same verdict and every verdict can be replayed from the ledger. A governance system whose answers vary between runs is not a governance system.

System architecture

The clearing path

A single endpoint carries the product’s whole argument. POST /api/trust/a2a/authorize is where an agent asks to spend on behalf of a human, and it is the point at which every pillar has to hold simultaneously. Four gates can reject the request; the fifth records it.

Escrow and recourse

Escrow is what turns a policy engine into a clearing house. Funds leave the sender’s balance at authorization but do not reach the receiver until the receiver signs for the work. That signature — or its absence — is what arbitration turns on.

Delegation chains

The pillar with the least prior art is delegation. An agent acting alone is a curiosity; an agent acting for someone, within limits that someone set, is commerce. Mandates make that relationship explicit, signed, and narrowing.

Where the architecture is load-bearing

Three of these gaps are ordinary engineering — swapping SQLite for Postgres or stdlib HTTP for FastAPI changes no guarantee the system makes. Three change what the system can honestly claim, and they are the real roadmap.

Key custody

While the server can sign on an agent’s behalf, it can also forge that agent’s intent. Custodial mode is right for a demo and disqualifying for production. Removing auto_sign is what makes the identity pillar mean what it says.

Ledger anchoring

The chain detects tampering by anyone who edits a row. It does not detect an administrator who rewrites the chain wholesale. Periodic checkpoints notarized outside the database close that hole.

Settlement

Escrow currently moves numbers in a table. Attaching real rails is what converts a governance product into clearing infrastructure — and brings regulatory scope with it.

Management authentication

The trust API verifies signatures on every call. The platform API beneath it does not authenticate at all, so the registry that trust decisions read from is currently writable by anyone who can reach the port.
